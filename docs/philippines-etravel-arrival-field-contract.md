# Philippines eTravel Arrival Field Contract

> Canonical contract v0.2, compiled/proposed by PH-A, pending coordinator approval, 2026-08-01（Asia/Singapore）.
>
> Scope: `PH_ETRAVEL_ARRIVAL_CARD` ordinary Filipino/Foreigner passenger arrival only. This document is a proposed canonical interface for PH-B schema, PH-C runner, and PH-D frontend work until the coordinator approves or supersedes it.

## Contract Semantics

- Dotted canonical keys such as `traveller.passport_number` are semantic paths, not required persisted `visa_form_fields.field_name` values.
- PH-B must not bulk rename existing flat DB field names just to match dotted keys. Existing flat keys may remain as persisted form field names where they are compatible.
- Applicant form answers must have a current flat key or a documented legacy alias. Where no current flat key exists, the contract says `none` and the item remains `needs_review` or requires a schema addition by PH-B.
- Account OTP/password, summary actions, final submit actions, and result artifacts are not applicant form questions and must not be inserted into `visa_form_fields`.

## Data Categories / Owners

| Category/owner | Meaning | Persistence boundary |
| --- | --- | --- |
| `applicant form answer` | User-provided travel/profile/customs/currency answer used for the eTravel declaration. Owner: application answer schema. | May live in `visa_form_fields` / application answers if in v1 scope. |
| `VIZA eligibility-only` | VIZA-only routing/diversion data. Owner: PH frontend eligibility and PH-C runner guard. | Must not be submitted as ordinary official passenger answers. |
| `account runtime secret` | eTravel/eGovPH login secret or OTP. Owner: secure runtime/account subsystem. | Must not enter `visa_form_fields`, application answers, test fixtures, docs examples, or logs. |
| `account runtime data` | Non-secret account runtime identifier, such as email used for eTravel account/login. Owner: account/runtime subsystem. | Do not treat as a visa form field unless PH-B separately maps an official applicant contact field. |
| `static notice/action` | Informational copy, acknowledgements, navigation, review, submit, or UI action. Owner: frontend/runner control flow. | Not an applicant question unless an explicit acknowledgement answer is separately listed. |
| `submission result` | Official reference, QR, screenshots, artifacts, or result status. Owner: submission result/artifact subsystem. | Never in `visa_form_fields` or applicant answers. |

## Status Values

Only these statuses are valid in this contract:

| Status | Meaning |
| --- | --- |
| `verified_public` | Public official page, official public frontend build, or first-round code audit proves the field/path/value exists. This does not imply full Review parity unless required/option/file details are explicitly listed. |
| `needs_review` | The item exists or is expected in the public official flow, but requiredness, complete option codes, file constraints, DOM control, official key conflict, or Review behavior needs stop-before-submit official verification. |
| `unsupported_v1` | The item must be diverted or blocked from ordinary passenger arrival v1. It must not be submitted through the ordinary `PH_ETRAVEL_ARRIVAL_CARD` path. |
